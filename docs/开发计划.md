# DevLauncher - 个人开发机项目管理器

> 本文档为项目方案评审级开发文档，覆盖定位、架构、模块、数据模型与风险权衡。
> 完整 SQL DDL、Tauri Command 清单、目录结构、接口签名留待详细设计阶段产出。

---

## 一、项目定位

### 1.1 一句话定位

面向**个人开发机**的轻量级项目管理工具。

### 1.2 核心目标

- 统一管理 Java、Node、Docker 等多种技术栈项目
- 以「**项目**」为中心，而非「**进程**」为中心
- 提供启动、停止、重启、构建、一键发布能力
- 实时监控项目运行状态（PID / CPU / 内存 / 端口）
- 单机使用，无需部署服务端
- 单 EXE 分发，开箱即用

### 1.3 目标用户

- 同时维护多个本地服务的全栈 / 后端开发者
- 经常在 SpringBoot、Node、Docker Compose 服务间来回切换的开发者
- 希望用一个统一控制台替代多个 IDE Run Configuration、PM2、Process Explorer 的开发者

### 1.4 典型场景

| 场景 | 痛点 | DevLauncher 提供的能力 |
|---|---|---|
| 早晨开机要拉起 5 个微服务 | 挨个 IDE 点启动，繁琐 | 分组一键启动 |
| 排查"谁占了 8080" | `netstat` 手动查 | 端口监听状态一目了然 |
| 重启 SpringBoot | stop IDE → wait → start | 一键重启 / 一键发布 |
| 看实时日志 | 多个终端窗口 | 日志中心统一查看 |

### 1.5 非目标（明确不做）

- ❌ 不做服务端 / 多机集群管理（单机工具）
- ❌ 不做企业级 RBAC / 多用户协作
- ❌ 不做 CI/CD 流水线（只做本地 build，不接 Jenkins/GitLab CI）
- ❌ 不做生产环境监控（仅开发机）
- ❌ 不做容器编排（仅封装 `docker compose up/down`，不做 K8s 替代品）

## 二、技术选型

### 2.1 客户端

| 技术 | 角色 | 选型理由 |
|---|---|---|
| **Tauri 2.x** | 桌面外壳 | Rust 后端 + WebView 前端，**安装包体积小（~5MB 级）**、内存占用低；对比 Electron 动辄 100MB+ 更适合「单 EXE」目标 |
| **Vue 3** | 前端框架 | 组合式 API + 响应式，适合实时状态刷新场景 |
| **Element Plus** | UI 组件库 | 表单 / 表格 / 树形分组组件齐全，开发效率高 |
| **Pinia** | 状态管理 | Vue 3 官方推荐，TS 友好，比 Vuex 轻量 |

> **权衡：为何不选 Electron？**
> Electron 生态成熟但体积大、内存高；本项目是开发者本地工具，对体积敏感，Tauri 的 Rust 后端也天然适合进程管理这类系统能力操作。

### 2.2 系统能力（Rust）

| 库 | 职责 |
|---|---|
| **sysinfo** | 进程监控（PID / CPU / 内存） |
| **tauri-plugin-shell** | 命令执行（start/build/stop） |
| **tauri-plugin-fs** | 文件访问（日志读取） |
| **tauri-plugin-dialog** | 文件选择（注册项目时选目录） |

> **权衡：为何不直接用 PM2？**
> PM2 是「进程中心」，本项目是「项目中心」；PM2 主要面向 Node，对 SpringBoot/Java Jar/Docker 支持弱；PM2 需常驻 Node 环境，不符合「单 EXE」目标。

### 2.3 数据存储

- **SQLite**（通过 `tauri-plugin-sql`）
- 单文件数据库，随应用分发，无需额外配置

## 三、核心设计原则

### 3.1 项目中心化

传统的「进程中心」视角只看到散落的 `java.exe` / `node.exe`，无法回答「HR 系统现在跑没跑」。

**错误视角（进程中心）：**

```
java.exe   PID 12345
java.exe   PID 23456
node.exe   PID 34567
```

**正确视角（项目中心）：**

```
HR后端
├─ SpringBoot
├─ PID 12345
├─ Port 8080
└─ Running

HR前端
├─ Node
├─ PID 23456
├─ Port 5173
└─ Running
```

### 3.2 边界说明

- 「项目」= 一条注册记录 + 由它派生出的进程树
- 一个项目对应一组启动命令、一组端口、一份日志
- 进程本身是手段，项目状态才是用户关心的对象

## 四、系统架构

### 4.1 三层架构

```
┌─────────────────────────────────────────────┐
│   表现层 (Vue 3 + Element Plus + Pinia)      │
│   项目列表 / 状态监控 / 日志查看 / 分组管理   │
└──────────────────┬──────────────────────────┘
                   │ Tauri IPC (invoke / event)
┌──────────────────▼──────────────────────────┐
│   系统能力层 (Rust)                          │
│   进程管理 / 端口检测 / 日志读写 / 命令执行   │
└──────────────────┬──────────────────────────┘
                   │ tauri-plugin-sql
┌──────────────────▼──────────────────────────┐
│   数据层 (SQLite)                            │
│   project / group / log_ref / dependency     │
└─────────────────────────────────────────────┘
```

### 4.2 IPC 边界原则

- **Rust 层**：只做「需要系统能力」的事 —— 启停进程、读系统指标、读端口、读写日志文件、操作数据库。是**原子的、低层的服务**。
- **Vue 层**：负责业务编排与 UI 状态 —— 比如「一键发布」= 依次调用 stop → build → start，这层编排逻辑放前端。
- **不**在 Rust 里写复杂业务分支，**不**在 Vue 里直接调系统命令。
- 具体 Command 清单与签名留待详细设计阶段定义。

### 4.3 进程模型与日志流

```
DevLauncher 主进程 (Tauri)
   │
   ├─ 启动项目 → fork 子进程（独立进程组）
   │                │
   │                ├─ stdout ─┐
   │                └─ stderr ─┤
   │                           ▼
   │                   data/logs/{project}/{date}.log
   │                           │
   └─ Rust 后端 tail ──────────▶ Tauri Event ──▶ 前端日志面板
```

要点：
- 子进程与主进程**隔离**，主进程崩溃不应带走已启动的项目（或至少提供恢复机制）
- 日志先落盘，前端按需订阅，避免大日志全量推送到前端

## 五、功能模块

### 5.1 项目管理

**职责：** 项目的增删改查与分组组织。

- 支持操作：新增 / 编辑 / 删除 / 项目分组
- 项目类型：SpringBoot / Java Jar / Node / Docker Compose / 自定义命令

**项目注册示例：**

| 字段 | SpringBoot 示例 | Node 示例 |
|---|---|---|
| 名称 | HR后端 | HR前端 |
| 路径 | `D:\Project\HR` | `D:\Project\HR-Web` |
| 启动命令 | `mvn spring-boot:run` | `npm run dev` |
| 构建命令 | `mvn clean package` | `npm run build` |
| 端口 | 8080 | 5173 |

### 5.2 项目状态机

项目在不同操作下的状态流转：

```
        start()                            port not listening
  ┌──────────────┐  ┌──────────────┐  ┌──────────────────────┐
  │              ▼  │              ▼  │                      ▼
┌─┴────┐      ┌──┴───┐      ┌─────────┴──┐      ┌────────────────┐
│Stopped│◄────│Starting│      │ Running │──────►│ Running(Abnormal)│
└──────┘ stop└────────┘      └─────┬────┘      └───────┬────────┘
     ▲                              │ stop()             │ port recovered
     │            ┌─────────────────▼                    │
     │            ▼                                       │
     │      ┌──────────┐                                 │
     └──────│Stopping  │◄────────────────────────────────┘
            └──────────┘
```

| 状态 | 含义 |
|---|---|
| Stopped | 未运行 |
| Starting | 命令已下发，等待端口监听或 PID 出现 |
| Running | 进程存活 **且** 端口监听正常 |
| Running(Abnormal) | 进程存活，但端口未监听（疑似启动失败 / 仍在初始化） |
| Stopping | 已下发 kill，等待进程退出 |

### 5.3 生命周期控制

**统一接口（前端编排调用）：**

- `startProject(projectId)`：工作目录切到项目路径 → 执行 `start_cmd` → 记录 PID / 启动时间
- `stopProject(projectId)`：Windows 用 `taskkill /PID xxx /T /F` 结束**整个进程树**
- `restartProject(projectId)`：Stop → Wait Exit → Start
- `buildProject(projectId)`：执行 `build_cmd`，实时输出构建日志

**异常处理：**
- 停止时要求回收整个进程树，避免残留 `java` / `node` / `npm` 子进程
- 重启必须确认旧进程完全退出后再启动，否则端口占用启动失败

**一键发布：** Build + Restart 组合，流程为「停止 → 构建 → 启动」，适用于 SpringBoot / Java Jar。

### 5.4 运行时监控

**刷新周期：** 3 秒

**监控内容：**

| 指标 | 来源 |
|---|---|
| 是否运行 | sysinfo 进程查询 |
| PID | 启动时记录 |
| CPU | sysinfo |
| 内存 | sysinfo |
| 端口监听状态 | 端口检测模块 |

### 5.5 日志中心

- 启动项目时重定向 `stdout` + `stderr`
- 保存位置：`data/logs/{projectName}/{YYYYMMDD}.log`
- 支持：实时日志 / 历史日志查看 / 日志清空

### 5.6 端口检测

- 定时检测项目配置的端口（如 8080 / 5173 / 3306）
- 状态：`Listening` / `Closed`
- 异常判断：项目进程存活 **且** 端口未监听 → 标记「异常」

### 5.7 项目分组

- 支持分组：HR系统 / OA系统 / 中间件 / 测试项目 等
- 展示：

```
HR系统
├─ HR后端
└─ HR前端

中间件
├─ Redis
├─ Nacos
└─ MinIO
```

### 5.8 P1 功能（后续迭代）

- **Git 状态**：显示当前分支、未提交数量、未推送数量（调用 `git status` / `git branch`）
- **IDE 打开**：`idea64.exe <path>` / `code <path>`
- **Docker 支持**：`docker compose up -d` / `docker compose down`

### 5.9 P2 功能（后续迭代）

- **AI 进程识别**：识别 Claude Code / Cursor / VSCode Agent，并关联到其操作的项目
  - 展示例：`Claude └─ 启动了 HR后端`
- **项目依赖启动**：启动 HR后端时自动检测 Redis / Nacos，未启动则提示「是否同时启动依赖服务」

## 六、数据模型

> 本节给出**概念模型**（实体与关系），完整 SQL DDL 留待详细设计阶段。

### 6.1 实体关系

```
┌────────┐  1   N ┌─────────┐
│ group  │────────│ project │
└────────┘        └────┬────┘
                       │ 1
                       │
              ┌────────┴────────┐
              │ N               │ N
       ┌──────▼─────┐    ┌──────▼──────┐
       │  log_ref   │    │ dependency  │
       └────────────┘    └─────────────┘
```

### 6.2 实体说明

| 实体 | 职责 | 关键属性（概念级） |
|---|---|---|
| **project** | 一个被管理的项目 | name, group, type, path, start_cmd, build_cmd, expected_ports, pid, enabled, create_time |
| **group** | 项目分组 | name, order |
| **log_ref** | 日志文件索引（便于历史日志快速定位） | project_id, date, file_path, size |
| **dependency** | 项目间依赖关系（P2 依赖启动用） | project_id, depends_on_project_id |

> 说明：原文档仅有一张 `project` 表，本设计将其拆为 4 个实体以支持分组、日志检索与依赖启动。`pid` 等运行时态字段仅作缓存，权威状态以实时探测为准。

## 七、风险与权衡

| # | 风险 | 影响 | 权衡 / 应对 |
|---|---|---|---|
| R1 | **进程树回收不可靠** —— Windows `taskkill /T /F` 对某些 detached 子进程可能漏杀 | 孤儿进程残留，占用端口 | 启动时用独立 Job Object / 进程组；停止后二次校验端口与 PID |
| R2 | **日志体积膨胀** —— 长期运行项目日志无上限 | 磁盘占用增长 | 按日期分文件 + 按大小/天数轮转；提供日志清空入口 |
| R3 | **端口冲突与状态误判** —— 端口被其他程序占用 | 误报 Running 或启动失败 | 检测端口时同时校验占用者 PID 是否属于本项目进程树 |
| R4 | **单 EXE 体积与首启** —— WebView 运行时依赖系统，首启可能偏慢 | 首次启动体验 | Tauri 自带轻量 WebView；权衡后优于 Electron 体积 |
| R5 | **sysinfo 跨平台一致性** —— Windows / Linux 指标口径略有差异 | 多平台监控数值细微偏差 | MVP 聚焦 Windows，跨平台一致性作为已知限制 |
| R6 | **AI 进程识别误判** —— 仅凭进程名/参数推断项目归属可能误判 | 关联展示错误 | P2 功能，需基于命令行参数 + 工作目录双重校验，并允许人工修正 |

## 八、优先级分层

> 仅做功能优先级分层，不做版本号与工期规划。

- 项目注册（含分组）
- 启动 / 停止 / 重启
- 构建 / 一键发布
- PID / CPU / 内存监控
- 端口监控
- 实时日志

**完成后即可替代：** 多个 IDEA Run Configuration、PM2、部分 Process Explorer 使用场景，成为开发机统一项目控制台。

### P1（后续）

- Git 状态展示
- IDE 打开项目（IDEA / VSCode）
- Docker Compose 支持

### P2（后续）

- AI 进程识别
- 项目依赖启动
