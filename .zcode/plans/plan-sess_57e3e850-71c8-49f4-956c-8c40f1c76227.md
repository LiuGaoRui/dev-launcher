# 重启功能修复方案

## 根因总结

1. **顺序错误（核心）**：当前 `build → stop → start`。对「start 跑 build 产物」的项目（如 ai-info-hub 的 `pnpm run start`、SpringBoot 的 `java -jar`），build 时旧进程还占着产物文件（Windows 文件锁）和端口 → build 写入失败/不完整 → start 起不来或起旧产物。
2. **按钮过度限制**：`ActionBar.vue` 重启按钮 `disabled` 含 `!canBuild`，`handleRestart` 开头硬拦截无 build_cmd 的项目 → 纯 dev 模式 Node 项目（只有 dev/start 脚本）点不动。
3. **端口释放竞态**：后端 `stop_project` 调 `taskkill /F /T` 后立即返回，不等端口/PID 真正释放；前端只靠启动失败重试一次（600ms）兜底，偏弱。

## 修复方案（3 处改动）

### 改动 1：前端重启顺序改为 `stop → build → start`
**文件**：`src/views/ProjectList.vue` 的 `handleRestart`（208-277 行）

新编排逻辑（全程仍 `withBusy` 锁卡片）：
```
1. 停止（仅当运行中）：await stop → 后端此时保证端口/文件锁释放
2. 构建（仅当有 build_cmd）：await waitBuildDone → 失败则中断
3. 启动：await start → probeNow 确认
```
- 去掉开头 `if (!build_cmd) { 提示无法重启; return }` 的硬拦截
- 保留 `waitBuildDone`（10 分钟超时 + onDone 回调包装）和构建失败中断逻辑
- 启动重试保留（轻量兜底，后端已基本保证端口释放后成功率很高）

**注释同步更新**：`build → stop → start` → `stop → build → start`，说明理由（先释放文件锁/端口再构建）。

### 改动 2：重启按钮放开可用性
**文件**：`src/components/project/ActionBar.vue`（66-77 行）

- 重启按钮 `:disabled` 去掉 `!canBuild` 条件，改为 `busy || buildRunning`
- `title` 文案改为：有 build_cmd → "停止 → 构建 → 启动"；无 build_cmd → "停止 → 启动"
- 头部注释（3-6 行）顺序描述同步更新

> 注：`canBuild` prop 仍保留给「构建」按钮用，不动。

### 改动 3：后端 stop_project 增加释放确认
**文件**：`src-tauri/src/commands/process.rs` 的 `stop_project`（124-176 行）

在 `kill_process_tree(pid).await?` 之后、`registry.remove` 之前，新增 best-effort 轮询确认：
- 复用现有 `pid_alive(pid, &system)`（sysinfo）确认进程已死
- 复用现有 `collect_tcp_sockets()` + `find_port_owner(port, &sockets)` 确认 expected_ports 已释放（从 DB 读 ports，与 stop_project 现有的端口发现逻辑同源）
- 轮询参数：间隔 300ms，最多 10 次（≈3s 上限）
- **超时不报错**：到达上限即放行（best-effort），仅 `tracing::warn!` 记录
- 无 expected_ports 的项目：只轮询 PID 释放

封装为 `stop_project` 内的局部辅助逻辑或私有函数 `wait_process_released(state, pid, ports, max_attempts)`，不暴露为 IPC 命令。

**前端配套简化**：`stop_project` 返回后端口基本已可用，前端 `handleRestart` 的启动重试从"失败才等 600ms"可保留，但不再依赖它兜底核心竞态。

## 不改动的部分
- `kill.rs` 的 `taskkill /F /T` 实现不动（只是调用方加确认轮询）
- `build.rs`、`spawn.rs` 不动
- build store 的轮询/onDone 机制不动
- project store 的 `start`/`stop`/`probeNow` 不动
- api 层不动（无新 IPC 命令）

## 验证
- `pnpm typecheck` 通过
- `cargo check`（src-tauri/）通过
- `cargo test`（process 模块单测）通过
- 手动验证：对 ai-info-hub（有 build_cmd）点重启 → 先停 → 再构建 → 再启动，全程产物/端口不冲突；对纯 dev 项目（无 build_cmd）点重启 → 停 → 启

## 风险与权衡
- **空窗期变长**：`stop → build → start` 比 `build → stop → start` 多一段"停了等 build"的服务空窗。对本地开发机工具可接受（重启本就有空窗，且能避免 build 失败导致的"旧服务被停 + 新服务没起来"更糟情况）。
- **后端 stop 变慢**：增加最多 ~3s 轮询。绝大多数情况下 taskkill 后端口几十 ms 内释放，实际几乎不等待；极端慢释放才用满 3s。
- 兼容性：Java 项目（`java -jar` 锁 jar）同样受益，不存在回归。
